# Prototype spec: climb/index.html

The exact specification the prototype was built from (2026-10-18). Any new version must keep it, especially the
harness contract in `../README.md`. If you change the spec, record why in `../DECISIONS.md`.

```text
PRODUCT CONTEXT
Kafu is a Telegram Mini App for medical MCQs (students mostly in Iraq, 86% Android, many cheap 90-120 Hz phones such as Helio G36/G81 class). The owner wants to explore a 2D game mode: a character starts at START, an arrow says "First MCQ"; tapping it makes the character move; the MCQ opens with its explanation, comments and video; tapping "Next MCQ" closes the MCQ very fast, the world returns and the character climbs (stairs, elevator) to the next question: one continuous story. Non-negotiables: FAST with no glitches, FREE, PROFESSIONAL. It must NOT be integrated into the app now. This prototype exists to let the owner feel it on a phone and to produce measurements.

Research already settled (follow it):
- Rewards come AFTER grading (repo rule docs/DESIGN.md:9 "Never celebrate before an answer is actually scored"). So the character walks to a "?" checkpoint sign that opens the MCQ; the coin is earned on the ledge only after answering, and collected when the world returns.
- Wrong answers are neutral, never punitive (DESIGN_STYLE.md study-core rule 5): a wrong answer still moves the climber forward, earns a smaller silver coin (+5 XP, mirroring app/modules/xp-ledger.js: new correct 10, new wrong 5) and plants a small "saved for review" flag. No falling, no lives, no shaming copy.
- Art style is Kafu "Arcade-Clean", NOT pixel art and NOT Mario-like: chunky rounded shapes, thick 2-3px ink outlines, hard offset shadows (0 4px 0 ink), bright token colours. Original work only.
- Per-question time cost must stay small and always skippable (seductive-details research: harm grows when learners cannot control pacing). Story mode target: Next -> next question readable in about 1 s; an elevator "story beat" every 4th question may take about 1.6 s. Tapping anywhere on the world during movement skips straight to the next MCQ.
- Tech: hand-written Canvas 2D, zero libraries (the app's start-up budget is full: 153,244 of 153,600 gzip bytes). One persistent canvas, never recreated. DOM MCQ sheet on top, animated with transform/opacity only. rAF loop runs only while something moves and stops while the sheet is open. Time-based motion with delta time (clamp dt to 50 ms) because many phones run rAF at 90/120 Hz. DPR capped at 2 (1.5 in low quality). No per-frame allocations, no shadowBlur, no canvas filters, no per-frame gradient creation, no per-frame text measuring: bake character frames, checkpoint signs (with their numbers), coins and parallax layers into offscreen canvases once (and re-bake on resize/theme change). Pre-build the next question's DOM during the climb.

FILE
Write ONE self-contained file: game-lab/climb/index.html. A full HTML document (<!doctype html>, <html lang="en">, <head>, <body>) so it opens from file://. No external requests at all (no CDN, no web fonts, no images by URL). Inline CSS and one inline 'use strict' script. Target size: at most 45 KB raw. Put <title>MCQs Mountain</title> and <meta name="claude:viewport-fit-sides" content="cover"> right after <meta charset> and the viewport meta (width=device-width, initial-scale=1, viewport-fit=cover). The page will also be published as a claude.ai artifact (its wrapper tags stripped by a script), so also follow these rules: colours only as CSS custom properties; the bare :root block defines every token with LIGHT values; then @media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { ...dark values...; color-scheme: dark } } and again :root[data-theme="dark"] { ...same dark values...; color-scheme: dark }; body sets background: var(--bg-token) explicitly. Copy the real values from app/design/tokens.css (light: primary #5B4CFF, accents #FFB703 and #00AFA0, background #FFF8E8, surface #FFFFFF, alt surface #FFF0CC, text #182032, muted #526079, success #177D4E, error #C93E4A, warning #9A5800; dark: primary #6A4CFF, accents #FFD166 #45D7C8, background #111522, surface #1B2132, alt #272E44, text #F8F7FF, muted #BEC5D8, success #65D998, error #FF818C, warning #FFD166) and its radius/spacing/motion tokens (motion 80/120/180/320 ms). The canvas reads its colours from these tokens (getComputedStyle) at bake time and re-bakes when the theme changes. If Telegram.WebApp is present and reports colorScheme, set data-theme accordingly. html, body height 100% (never 100vh); no horizontal scroll at any width from 320 px; anything fixed to an edge adds env(safe-area-inset-*) to its padding; the DOM UI wrapper uses padding-left: max(16px, env(safe-area-inset-left, 0px)) and padding-right: max(16px, env(safe-area-inset-right, 0px)). Fonts: display stack "Fredoka", ui-rounded, "Arial Rounded MT Bold", system-ui, sans-serif (titles, numbers, short game labels only); reading stack "Nunito", ui-rounded, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif (ALL stems, options, explanations). Study text never uses the display font. Every tappable control is a real <button> at least 44x44 CSS px with a visible focus ring. Avoid very new web features without fallback (no CSS nesting, no :has(), no structuredClone); must run on Android WebView (Chromium) and iOS 15+ WKWebView. Wrap any localStorage access in try/catch (you may skip storage entirely).

WORLD: "MCQs Mountain" (the repo's own name)
- Side view of a mountain path rising up and to the right. Checkpoint i sits on a ledge; consecutive checkpoints are joined by a staircase of 3 steps; every 4th transition (3->4, 7->8) is an elevator/cable-lift platform that rises instead (a story beat). After the last question the character walks to a summit with a flag.
- Camera follows the character smoothly (critically damped / lerp, time-based), framing the character in the upper part of the screen so the bottom sheet can cover the lower part.
- Layers: sky as a CSS gradient behind a transparent canvas (zero texture memory); far mountains and mid hills baked once into offscreen canvases, drawn with drawImage at parallax offsets (parallax off in low quality); ledges and stairs drawn from a few baked tile sprites with ink outline and hard shadow; checkpoint sign = rounded square block with "?" and its number "Q3", baked per number.
- Character: an ORIGINAL placeholder climber drawn with canvas paths ONCE into a baked frame atlas at 2x: a round-headed young medic with a white coat, a primary-colour backpack and a small stethoscope, big friendly eyes, thick ink outline, hard shadow. Frames: idle (2), walk (4), step/hop (2), cheer (2). About 56x64 CSS px on screen. Mark it in a code comment as a placeholder until the real character art exists.
- Coins: gold coin (+10) for correct, silver coin (+5) for wrong plus a small flag; on world return the coin pops up with a floating "+10 XP"/"+5 XP" label (baked text) and the character collects it.

FLOW AND STATES (window.__lab.state)
- 'start': character at a START banner. Start panel (DOM): title "MCQs Mountain", subtitle "Sample chapter · 8 MCQs", a three-option segmented control for the mode (Story / Strip / Classic) each with a one-line description, and a big pressable arrow button "First MCQ ->" with data-lab="go" that gently bobs (CSS transform animation, disabled under reduced motion). The canvas is static (loop stopped) while waiting.
- Tap go -> 'moving': walk to checkpoint 1 (about 600 ms) -> the MCQ sheet slides up (200 ms, transform translateY + opacity, ease-out). On the first animation frame after it is fully open: performance.mark('lab:sheet-visible'), state 'question', rAF loop stopped.
- The MCQ sheet (bottom sheet covering about 78% of the height, scrollable inside, max-width 560 px centred on tablets): header "Q n/8" + type chip (Single best answer / True-False / Choose two / Extended matching) + XP; lead_in for EMQ; stem; options as buttons with data-lab="opt" (sba/emq: single select; multi: select exactly two; mtf: each statement has True and False buttons, each with data-lab="opt"). A "Check answer" button (enabled when the response is complete, exactly like the app's isComplete). After grading: feedback with icon + text + colour ("Correct" / "Not quite: the answer is C", neutral wording; mtf shows each statement right/wrong and the score), per-option correct/wrong marking, the explanation, then two placeholder rows "Comments · 12" and "Watch the lesson" (each opens a small inline panel that says it is a placeholder for the app's real comments sheet / MotionCards player, not connected), then the primary "Next MCQ" button with data-lab="next" (on the last question it reads "Finish chapter"). An aria-live region announces the result. When the sheet opens, focus moves to its heading.
- Grading must copy the app's rules (app/index.html grade() around lines 786-800): sba/emq compare one letter; mtf correct only when every statement matches, with partial score shown; multi needs the exact set.
- window.__lab.answer(): test hook that fills a complete CORRECT response for the open question (if not already graded) and grades it exactly as the Check button does.
- Tap Next -> performance.mark('lab:next-tap') immediately in the handler -> STORY mode: the sheet slides down (140 ms, ease-in); on the first frame where it is fully hidden performance.mark('lab:world-visible'); state 'moving'; the coin pops and is collected; the character climbs the stairs (about 600 ms) or rides the elevator (about 1200 ms on beats); then the next question's sheet (already pre-built) slides up and 'lab:sheet-visible' is marked as above.
- STRIP mode (the research's alternative): there is no world screen between questions. The sheet stays open; on Next the question content cross-fades (120 ms, opacity only) to the next question, and a 56 px "mountain strip" at the top of the sheet (a small canvas or the same canvas region showing the mini climber on a mini path with 8 ledges) animates the climber one ledge up (320 ms, non-blocking). Mark 'lab:world-visible' and 'lab:sheet-visible' when the new content is shown. Tap go still starts with a short walk then the sheet.
- CLASSIC mode: the baseline with no game at all: Next swaps the content instantly (no animation); marks as in strip mode. A plain progress bar instead of the strip.
- After the last question: Next -> (story: sheet down, coin, walk to summit, cheer) -> state 'done' -> a summary card (DOM): "8 MCQs · 6 correct · +70 XP", "Time reading and answering: m:ss", "Time added by the game: X.X s (Y.Y s per MCQ)", "At this pace 100 MCQs would add about Z min", "Animations skipped: n", and a "Climb again" button that resets everything (and the mode picker). Game time = sum over transitions of (sheet-visible - next-tap), plus the first walk. Be honest: classic mode shows about 0.
- Skip: during 'moving', a tap or click anywhere on the world (or the Space/Enter key) finishes the movement instantly (character placed at the destination, coin collected) and opens the sheet; count skips. A small hint "Tap to skip" shows during movement (not under reduced motion, where movement is already instant).
- Reduced motion (prefers-reduced-motion: reduce, or ?rm=1): all movement and sheet transitions are instant cuts; a text label "Ledge 3 of 8" in the HUD carries the progress; no bob, no cheer animation, no parallax drift.
- HUD (DOM, top, respects safe-area top): XP counter (display font), "Ledge n/8", a sound toggle (sound OFF by default; optional tiny WebAudio oscillator blips for coin and step like app/design/game-feel.js; no audio files).
- Telegram (only if globalThis.Telegram?.WebApp exists; the file does NOT load telegram-web-app.js): ready(), expand(), setHeaderColor/setBackgroundColor to the bg token, disableVerticalSwipes() when isVersionAtLeast('7.7'), HapticFeedback.impactOccurred('light') on coin collect, onEvent('activated'/'deactivated') and document visibilitychange pause/resume the loop (reset the frame clock on resume so nothing jumps). Low quality when navigator.userAgent contains "LOW)" (Telegram Android performance class) or ?low=1: DPR 1.5, no parallax.
- Debug overlay (?debug=1): fps, frame-time p95 over the last 120 frames, frames over 33 ms, whether the loop is running.
- Questions: use these 8 from the app's own SAMPLE data in app/index.html (lines about 299-360), copying stem, options, answer, explanation, lead_in, no_shuffle exactly: Q000000001 (sba), Q000000003 (mtf), Q000000006 (sba), Q000000007 (multi), Q000000011 (emq), Q000000008 (mtf), Q000000013 (sba), Q000000012 (emq). Do not shuffle (keeps tests deterministic).
- Expose window.__lab = { state, mode, answer(), version: 1 } and keep state accurate at every step ('start' | 'moving' | 'question' | 'done').

QUALITY BAR
This should feel like a polished small mobile game, not a tech demo: easing with a little squash and stretch on landing, a satisfying coin pop, crisp edges at DPR 2, consistent outlines, readable study text, calm sheet. But never at the cost of speed: smoothness on a weak phone wins over decoration.
```

## The four reviews still to run (Gate 0)

Each reviewer reports findings as blocker / major / minor, with evidence and a concrete fix. Then one agent fixes the
confirmed findings, and a different agent re-measures and takes final screenshots (screenshots are not committed).

### speed

```text
You are a performance engineer for mobile web games. Measure and diagnose the prototype at game-lab/climb/index.html.
1. Run the harness for every mode (story, strip, classic) at --cpu 1,4,6 with --q 8, saving JSON to <scratch>/perf/review-<mode>.json. Also run story mode with reduced motion (write a tiny variant runner that sets reducedMotion: 'reduce' on the context, or load with ?rm=1) and with ?low=1.
2. Profile story mode at 6x CPU with a Chrome trace (page.context().tracing or CDP Tracing) or the Performance API, and find the root cause of every frame over 33 ms and every long task: allocations in the hot loop, layout reads, style recalculation, oversized canvas, re-baking at the wrong time, image decoding, GC.
3. Read the code for anti-patterns: per-frame allocations, shadowBlur/filter, per-frame gradient or text, canvas resize on every frame, loop not stopping when idle, missing dt clamp, not resetting the clock after pause, DPR not capped, layout-triggering properties animated in CSS.
Targets: at 4x CPU, frame p95 <= 16.7 ms and p99 <= 33 ms during movement, no long task over 50 ms during transitions, Next input to first frame < 100 ms; story Next -> next question about 1 s normal and about 1.6 s on beats; strip and classic Next -> next question under 150 ms. Report every miss as a finding with the measured numbers and a concrete fix.
```

### qa

```text
You are a ruthless QA engineer. Break the prototype at game-lab/climb/index.html with scripted Playwright sessions and report every bug with an exact repro.
Cover: all three modes to 'done' and "Climb again"; every question type answered correctly AND wrongly (check grading against the app's grade() rules in app/index.html lines about 786-800, e.g. mtf partial, multi exact set, emq single letter); double/rapid taps on go, Check and Next; tapping the world during movement (skip) including spamming it; tapping Next during the sheet transition; resizing the viewport and rotating to landscape mid-movement and while the sheet is open; reduced motion (context reducedMotion 'reduce'); dark mode (colorScheme 'dark'); keyboard-only play (Tab/Enter/Space); viewports 320x568, 360x740, 390x844, 820x1180 (iPad) and 1280x800; that __lab.state is always accurate; no console errors; no horizontal scroll (document.documentElement.scrollWidth <= innerWidth); no overlapping or clipped text in the sheet; focus moves to the sheet heading; aria-live announces results; the summary numbers are consistent (XP = 10 per correct + 5 per wrong; game time about 0 in classic). Severity: blocker = stuck state, crash, wrong grading; major = visible glitch or broken control; minor = polish.
```
