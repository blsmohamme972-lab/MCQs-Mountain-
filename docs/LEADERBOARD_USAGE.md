# Leaderboard summaries and daily D1 usage

The leaderboard now reads indexed score summaries, never the answer history. Compact 4096-question attempt buckets retain lifetime first-attempt deduplication, including incorrect answers. A revision-guarded ledger replacement and SQL trigger update total and current Baghdad-week scores together. The migration backfills existing scores and attempts once. Historical rows and compatibility triggers remain so the previous Worker can receive answers during staged deployment; the new Worker never appends per-question rows.

Top 30 snapshots refresh on demand once per ten minutes. Cached boards make no writes. Personal rank is removed. The device shows its last server-verified score and computes `max(0, cutoff + 1 - score)` from the cached #30 score, without another D1 read when opening the board. One extra point avoids promising a place on a tie. Before this device has a verified submission score it asks for an answer batch to sync, rather than inventing a points gap. Privacy changes immediately invalidate snapshots. Weeks reset Monday 00:00 Baghdad time; old weekly scores do not appear in a new week.

The device retains downloaded books/images, progress and pending submissions. Leaderboard failures never block recording an answer. Submissions send up to 100 first attempts per batch, at 100 queued attempts or once per hour while the app is open. Closing preserves the durable pending queue; reopening resumes scheduling. Submissions are single flight and time out after ten seconds; failures back off from one minute up to one hour. Offline queues are not truncated at 500 anymore. The saved student-progress format and download/sync code are unchanged.

A 500-answer fixture uses five batches across two buckets: twelve table changes, plus an estimated twelve ranking-index writes, about 24 D1 writes for an existing student, plus five daily usage-counter updates (about 29 total). Registration/profile changes, crossing more buckets, and small sessions add overhead. This is a workload model, not a hard daily cap or a measured Cloudflare bill. The dashboard reports actual Cloudflare row metrics.

## Admin usage panel

The dashboard feature branch was inspected and contains only planning documents (draft PR #49), so this PR adds a small read-only inventory/usage view without changing that branch. The Me entry appears only after `/admin/capabilities` verifies signed Telegram initData and the runtime `ADMIN_IDS` allowlist (defaulting to the existing owner). Admin sessions expire after 24 hours. Endpoints use `private, no-store`, and no admin payload is saved to device storage or service-worker caches. Data is cleared when the Telegram session changes.

The D1 panel reads Cloudflare's `d1AnalyticsAdaptiveGroups` rowsRead/rowsWritten, not query counts or estimated student counts. It shows account-wide daily totals over seven UTC dates against 5,000,000 rows read and 100,000 rows written. A warning appears at 70% of either free limit. Daily allowances reset at 00:00 UTC / 03:00 Baghdad. Cloudflare reporting can lag; an absent day's metrics stay unavailable rather than being shown as zero. Analytics responses are reused for five minutes per Worker isolate.

Deployment passes the existing Cloudflare account ID and a server-only analytics token. `D1_ANALYTICS_TOKEN` is preferred; if absent, the existing deployment `CLOUDFLARE_API_TOKEN` is used. The token must have account analytics read access. CI checks the exact server query against the configured account before merge, without logging IDs, credentials or metrics. If permission is missing, the panel explicitly shows analytics unavailable; it never invents counts. No token, administrator ID or account analytics payload is public or committed.

Sources: https://developers.cloudflare.com/d1/observability/metrics-analytics/ and https://developers.cloudflare.com/d1/platform/pricing/.

Publishing still dispatches immediately for uploads and existing owner publishing actions. Only the recovery cron changes, from every 15 minutes to once daily at 03:00 UTC.

Validation includes migration/legacy overlap, duplicate/concurrent retries, score preservation, weekly boundaries, cached Top 30 and cutoff, privacy invalidation, workload/write modelling, admin access denial and analytics errors, offline pending durability, single-flight submission, and 360/390/430 light/dark admin layout/account-isolation journeys. Existing visual baselines are unchanged.

## Bounded submission reads (follow-up)

Migration 0005 adds a revision column and a daily usage table. Existing JSON ledgers, score summaries and historical per-question rows remain readable. New submissions read each touched bucket once, build a Set in Worker memory, and write it once if there are fresh IDs. No JSON virtual-table scan runs in the new submit SQL. Compare-and-swap on revision prevents lost updates and double awards. A conflicting request returns 409 instead of rereading the bucket; the existing durable client retries it. If earlier buckets already committed they dedupe on retry. Compatibility revision updates also cover the previous Worker, without firing the scoring trigger twice. No new per-question answer rows are written by either the current or proposed Worker.

Every D1 endpoint logs request totals from actual `meta.rows_read` / `meta.rows_written`, with no SQL, bind values or identities. Worker observability is enabled. Submission totals across isolates are persisted in a single UTC-day counter, one additional row update per database-using submission. Admin reads/submission and peak reads come from these counters, include retries/errors, and exclude the counter update itself. That update logs its own actual D1 metadata as `d1_telemetry_usage`; account-wide usage includes it. Missing metadata is marked unmeasured, never replaced with a guessed zero. The admin panel also displays `meta.size_after` in bytes and MiB. CI reads the production database metadata with GET to report the current `file_size` without modifying it.

The pinned local workerd/Miniflare test runs the real Worker code against D1 bindings and asserts equal billed-row counters at history sizes 0, 1,000 and 3,996, for both one-answer and 100-answer batches. It also asserts one read and zero writes for a cached board. These local runtime measurements validate query behavior; production per-endpoint logs and the admin totals remain authoritative for actual usage. Offline books/images/progress formats and daily publishing backup are unchanged.
